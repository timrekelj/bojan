# CLAUDE.md

Self-hosted, single-guild Discord bot (TypeScript ESM, Node >= 22.5, discord.js 14, built-in `node:sqlite`). It tracks message/reaction/voice/activity stats, posts weekly stats, converts embed links, announces free games, and serves a Hono dashboard with Discord OAuth. Charts are rendered to PNG with `@resvg/resvg-js`. User-facing docs and setup live in `README.md`; this file covers working in the code.

## Module map (`src/`)
- `index.ts`: startup wiring (db, client, web server, weekly scheduler) and shutdown.
- `config.ts`: env vars into `config` (required vars throw at import; `guildId`, `databasePath`, ...).
- `bot.ts`: client and intents, slash command definitions, per-guild registration, event handlers, `/backfill`.
- `db.ts`: `BotDatabase`, the only SQL access (schema, migrations, queries, key/value `bot_state` table).
- `stats.ts`: pure time/week/timezone math and leaderboard formatting.
- `levels.ts`: MEE6-style leveling — pure XP roll/level math, `awardMessageXp` (30s per-user cooldown, `user_xp` table), Components V2 level-up card; toggle + channel in dashboard settings.
- `weekly.ts` / `cards.ts`: Components V2 message builders (weekly stats; leaderboard and activity).
- `chart.ts`: SVG-to-PNG daily chart (resvg uses system fonts; the Dockerfile installs DejaVu).
- `scheduler.ts`: 30s tick that posts last week's stats once per week (`weekly:<guild>` state key).
- `embeds/`: `providers.ts` (pure link detection and rewriting), `converter.ts` (webhook repost of the converted link).
- `freegames/`: `types.ts`, `filters.ts` (`isBetaTitle`, `matchesFilters`, `filterGames`), `freestuff.ts` (FreeStuff webhook verify + normalizer), `cards.ts`, `form.ts` (dashboard form parsing), `actions.ts` (`announceInGuild`, `announceEverywhere`, `titleDedupeKey`).
- `web/server.ts`: Hono routes, OAuth, settings POST handlers. `web/views.ts`: server-rendered HTML and CSS.
- `builder/chat.ts` + `chat-parse.ts` (chat assistant): any member's @mention opens a thread backed by one OpenCode session (agent `chat`, `.opencode/agents/chat.md`, web search + read-only access to a checkout of `main` at `/workspace/bojan`, refreshed with `OpenCodeAgent.refreshMain` before each new chat session); the bot only answers messages that @mention it or reply to one of its messages (`isDirectedAtBot`); every other thread message produces no model call, reaction or typing and is buffered in memory per thread as context (`ThreadState.context`), prepended to the next directed turn under "Other messages in the thread since your last reply" (`formatThreadContext`). Directed messages are batched (3s debounce, serialized per thread) and always answered when the agent produced visible text (the json `reply` flag is ignored). The decision model `chatDecisionModel` (default `opencode-go/jev-1.14`, `OpenCodeAgent.decide` → `experimental.generate.decisions`, predicate `FEATURE_REQUEST_QUESTION`, `isFeatureRequest` threshold 0.5, 15s timeout; failure = plain chat) runs only for a directed (@mention) message from an admin while building is enabled and configured (`shouldRunDecision`; also for one-off mentions, before any session is created), and sees the last ~30 thread messages before it (history, clipped to 6000 chars), the replied-to message and the "Latest message (the one to classify)" (`formatDecisionInput`), so a short "ship this" / "build it" referring to a bot change discussed earlier counts as a feature request while discussing alone does not. If it says yes the chat agent is skipped: the build job starts in the same thread (`BuilderRunner.startJob` with the plain request text from `featureRequestText` and a transcript of up to 50 recent messages; the planner prompt says the request may refer to the discussion in the transcript, which never approves a plan) and "Got it, I'll make a plan for this." is posted only after `startJob` succeeded; pending notes stay for the next chat turn; after the job ends the thread is chat again. Everyone else (non-admins) who mentions the bot goes to the chat agent, which, for a change request, asks them to say clearly what to build (e.g. "@bojan build <the change>") or to say "ship this" after discussing it in the thread. The agent ends with a trailing json block `{reply}`; a reply without a valid block is never posted (asked once more, then dropped, `ChatReply.missingBlock`). Build status changes queue `[build update]` notes (`formatBuildNote`, `chat_threads.pending_notes`) that are prepended to the thread's next chat prompt (no model call of their own). Mentions inside foreign threads are one-off replies. State: `chat_threads` table, `chatEnabled`/`chatModel`/`chatDecisionModel` in `getBuilderSettings`. `chat-parse.ts` is pure (reply parsing, chunking to 2000 chars, prompt formatting). The `[build status]` block (`formatJobStatus`, `jobStatusBlock`) for the thread's newest in-flight job is prepended to chat turns, so chat keeps working during a job; while a job is active the decision model is skipped (no second job). `chat-parse.ts` also has `pickReplyTarget`. Feedback is via reactions (`builder/reactions.ts`): directed messages (mention or reply to the bot) get the guild's `hmmmm` emoji (fallback 🤔) until the turn ends, typing is shown only for turns with a directed message, and the first reply chunk is a Discord reply to the target message. The runner has no typing indicator: 📝 on the triggering message while planning, 🔨 on the plan message while building, then ✅ (PR opened) or ❌ (failed); `updatePresence` sets the bot activity to `Building <title>` (`buildingActivity` in `queue.ts`).
- `builder/` (self-building): `queue.ts` (pure: queue order/slots, recovery decision, conflict action, resume/fix prompts), `parse.ts` (agent reply/json parsing, `prInfoFromJson`, naming, usage formatting, admin check; pure), `cards.ts` (Components V2 cards, pure), `opencode.ts` (`@opencode/client` wrapper: warm location, git worktree via shell, session, prompt-and-wait, usage), `runner.ts` (orchestration: plan Q&A in parallel per thread, build queue limited by `maxParallelBuilds` (statuses `queued`/`building`, FIFO by `approved_at`, drained when a build ends, on a 30s tick and after recovery), restart recovery that resumes interrupted sessions (max 2, `resume_count`), PR tracking via GitHub API every 2 min with one automatic merge-conflict fix per PR (`fix_attempts`)), `handler.ts` (messageCreate: thread messages feed the runner while a job is active, otherwise the chat assistant; in the planner phase only directed messages (mention or reply to the bot, e.g. to the plan card) trigger a turn via `handleReply(..., { trigger })`, other messages are context only (`preContext`, header "Other thread messages since your last reply") and can never approve; no bot output for non-directed messages in any path). Jobs live in `build_jobs` (a thread may hold several over time; `getBuildJobByThread` returns the newest); settings via `getBuilderSettings` (bot_state). Needs `OPENCODE_PASSWORD`; agents are defined in `.opencode/agents/`.
- `smoke.ts`: offline test script.

## Commands
- `npm run dev`: `tsx watch src/index.ts`. Needs env vars; `tsx` does not load `.env` by itself.
- Run locally with a throwaway DB, so the real `data/bot.db` is untouched:
  `DATABASE_PATH=/tmp/bojan-dev.db npx tsx --env-file=.env src/index.ts`
- `npm run build`: `tsc -p tsconfig.json`. This is the typecheck; there is no linter. Run it before finishing.
- `npm run smoke`: offline tests in `src/smoke.ts` (temp DB, no Discord token). Known weekday-dependent flaky failures: "last week total", "current week total", "top channels last week" and "per-day counts". Don't chase these unless you touched week math.
- `npm start` runs `dist/index.js`. Docker: `docker compose up -d --build`; the `data/` volume holds the DB.

## Rules and conventions
- **All settings are configured only in the dashboard** (`web/server.ts` and `web/views.ts`). Never add settings slash commands. Slash commands are read-only (leaderboard, activity, ...); the one exception is the admin-only `/backfill` action.
- Single guild: use `config.guildId`. Commands are registered per guild by PUTting the full command array in `registerCommands` (`bot.ts`); a new command must be added to the `commands` array there, or it won't register.
- Database: go through `BotDatabase`. The schema is in the `CREATE TABLE IF NOT EXISTS` block in `db.ts`. Add columns to existing tables via a migration: check `PRAGMA table_info(<table>)`, then `ALTER TABLE ... ADD COLUMN ... DEFAULT ...` (see `free_settings.include_beta`). Also update the `CREATE TABLE` so fresh DBs match. Use the `bot_state` key/value table (`getState`/`setState`) for flags such as "already sent" or "seeded".
- Discord messages use Components V2: build a `ContainerBuilder` and return `flags: MessageFlags.IsComponentsV2`. Text across all TextDisplays is capped at 4000 chars (`TEXT_BUDGET = 3800` in `cards.ts`; trim lines, never the headings). Use no-mention `allowedMentions` by default (`NO_MENTIONS` / `{ parse: [] }`). The only exception is the free-games ping role, `{ roles: [role] }`. Chat replies are plain text (≤2000 chars per message, split at line boundaries) with `allowedMentions: { parse: [] }`. The `chat` agent must stay read-only: no edits, shell limited to read-only `git log/show/diff/blame` and `ls`; keep its trailing json contract in sync with `parseChatReply`.
- Logging: `console.log/error/warn` with a `[tag]` prefix (`[bot]`, `[db]`, `[web]`, `[scheduler]`, `[freegames]`, `[embeds]`, `[builder]`, `[chat]`). Include the guild id where relevant. Background loops catch per guild and per item so one failure doesn't stop the rest.
- HTML: every dynamic value in `web/views.ts` goes through `escapeHtml`, including attributes.
- Keep pure logic (parsing, normalizing, filtering, formatting, builders) in exported functions that take plain data, so `smoke.ts` can import them. Add smoke tests for new logic; smoke checks are plain assertions in `src/smoke.ts`.
- ESM with NodeNext-style imports: relative imports end in `.js` (`from './db.js'`).
- Don't add dependencies without good reason; the dependency list is deliberately tiny.

## Free games
- Source: the FreeStuff webhook only, no polling (Epic's free games arrive through it with store `epic`) (`POST /webhooks/freestuff` in `web/server.ts`, logic in `freestuff.ts`, enabled by `FREESTUFF_PUBLIC_KEY`; push-only, no REST key). FreeStuff cards show `-# via FreeStuff`. Console products from FreeStuff are skipped.
- **Dedupe**: every announce marks both `g.key` and `titleDedupeKey(g)` (`t:<platform>:<store>:<normalized title>`) in `free_posted`, and skips a game if either is posted. Use `announceInGuild` / `markGamesPosted` / `isGamePosted` from `actions.ts`, not raw `markFreePosted`. The webhook is signature-verified (Ed25519), replay-guarded, answers 204 first and announces asynchronously.
- Everything is normalized to `FreeGame` (`types.ts`): `key` is a stable id (`fs:<id>`), `kind` is `game | dlc | beta`, `platform` is `pc | mobile`, and `store` is one of `ALL_STORES`. Beta/playtest/demo keys are detected by `isBetaTitle`.
- Filters (`FreeSettings`: `stores`, `includeDlc`, `includeBeta` (default off), `includeMobile`) are applied by `matchesFilters` / `filterGames`. A new filter needs: the type, a DB column plus migration, `form.ts` parsing, the dashboard view, and the smoke tests.
- **No backlog**: webhooks only deliver new announcements, so nothing is seeded on enabling the feature or changing filters. Announce dedupe uses `markFreePosted` / `isFreePosted`. The dashboard status shows whether `FREESTUFF_PUBLIC_KEY` is set and the announced count.

## Discord requirements
- Gateway intents (`bot.ts`): regular intents Guilds, GuildMessages, GuildMessageReactions, GuildVoiceStates; privileged intents MessageContent, GuildMembers, GuildPresences. The privileged ones must be enabled in the developer portal.
- Bot permissions: View Channels, Send Messages, Read Message History, Embed Links, Attach Files (weekly chart PNG), Manage Messages (embed converter deletes or suppresses the original), Manage Webhooks (embed converter reposts), Create Public Threads + Send Messages in Threads (self-building request threads), Add Reactions (status emoji; Use External Emojis is not needed). OAuth scopes `bot` + `applications.commands`. The dashboard allows Administrators or `ADMIN_ROLE_ID`. Setup details are in `README.md`; env vars are in `.env.example`.
