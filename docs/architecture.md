# Architecture details

Per-area behaviour of the bot. `CLAUDE.md` has the module map and the rules; this file has the detail. Read only the section for the area you are changing (grep for its heading).

## Core modules

- `index.ts`: startup wiring (db, client, web server, weekly scheduler) and shutdown.
- `config.ts`: env vars into `config` (required vars throw at import; `guildId`, `databasePath`, ...).
- `bot.ts`: client and intents, slash command definitions, per-guild registration, event handlers, `/backfill`.
- `db.ts`: `BotDatabase`, the only SQL access (schema, migrations, queries, key/value `bot_state` table).
- `stats.ts`: pure time/week/timezone math and leaderboard formatting.
- `weekly.ts` / `cards.ts`: Components V2 message builders (weekly stats; leaderboard and activity).
- `chart.ts`: SVG-to-PNG daily chart (resvg uses system fonts; the Dockerfile installs DejaVu).
- Weekly awards (`weekly.ts`, pure picks in `stats.ts`, data from `db.reactionMessageStats`): "Crowd pleaser" (reactions per message, needs >= `AWARD_MIN_MESSAGES` = 5 messages that week) and "Silent spectator" (needs >= `AWARD_MIN_REACTIONS` = 5 reactions given; ranked by lowest (messages + 1) / reactions given). Self-reactions don't count.
- `scheduler.ts`: 30s tick that posts last week's stats once per week (`weekly:<guild>` state key).
- `embeds/`: `providers.ts` (pure link detection and rewriting), `converter.ts` (webhook repost of the converted link).
- `smoke.ts`: offline test script.

## Monthly recap
- Two Components V2 messages (`monthly.ts`, pure builders `buildMonthlyRecapMessage` / `buildMonthlyAwardsMessage` over one `MonthlyRecapData`): stats (top messagers, channels, reactions, voice time, per-day chart, peak hours + heatmap) and awards (message of the month, crowd pleaser, silent spectator, biggest fan, night owl, early bird, conversation starter, streak, voice buddies, novelist, one-word replier, typo king). Each message keeps its text under 3800 chars by shrinking lists (3 → 2 → 1), never headings.
- Data: `gatherMonthlyData` (`scheduler.ts`) for `lastMonthBounds`; award logic is pure in `recap.ts` / `stats.ts`, where the thresholds also live (`NOVELIST_MIN_MESSAGES`, `BUDDY_MIN_MS`, `CONVO_GAP_MS`, night/early hours, `AWARD_MIN_*`). Edits/deletes come from `message_edits` (`botdeletes.ts` keeps the bot's own deletions out).
- Schedule: same tick as weekly, independent of `weeklyEnabled`; needs `monthlyEnabled`. Posts on the 1st at the weekly hour to the stats channel, catching up later in the month. State key `monthly:<guild>` holds the last handled month (`YYYY-MM`). First run seeds it to the current month without posting (no backlog; `monthlyAction`). If only the awards message fails, the month is still marked done so the recap isn't posted twice.
- Dashboard: "Weekly & monthly stats" card with the toggle and a "Send monthly recap now" button (`POST /monthly/send-now`, never touches the state key).

## Levels

`levels.ts`: MEE6-style leveling — pure XP roll/level math, `awardMessageXp` (30s per-user cooldown, `user_xp` table), `awardReactionXp` (1% chance per reaction, level + 1 XP; a win refreshes the message cooldown window), `awardVoiceXp` (10 XP per completed 10-minute voice block, paid by the `startVoiceXpTicker` loop in `scheduler.ts`), Components V2 level-up card; toggle + channel in dashboard settings. Voice sessions: `startVoiceXpTicker` also writes a per-guild `voice:heartbeat:<guildId>` timestamp every minute (even with leveling off); on `ClientReady`, `db.closeStaleVoiceSessions` closes open sessions of members no longer in voice (or in another channel) at that heartbeat (their `last_seen_at` if none yet), so downtime doesn't inflate voice time. The dashboard level badge is a hollow SVG outline (transparent fill, 3px stroke and level number in the band colour) using Steam-style colours via `steamLevelColors(level)` (`STEAM_LEVEL_BANDS`: the same 10-colour cycle repeats in every 100-level band, x0…x90) and a shape that changes every 100 levels via `steamLevelShape(level)` (`STEAM_LEVEL_SHAPES`, 900+ keeps the last shape; geometry in `STEAM_LEVEL_OUTLINES`), while the progress bar uses the same level-band colours via `--lv-from`/`--lv-to` (dark/light) on `.levelbar i`. The level number is centred in the 52x52 viewBox (`x="26" y="26"` plus `dominant-baseline="central"`).

`colors.ts` + `color_roles`/`color_settings` tables: name-colour reaction roles. The roles are pre-made; the dashboard ticks which ones are colours and picks a channel, and `POST /color-settings` posts one Components V2 message per role (with a 🎨 marker reaction) and deletes messages of unselected roles. Reacting to a message in `bot.ts` gives that role and removes the member's other colour roles (one per member; `rolesToSwap`), removing the reaction drops it. Needs Manage Roles and roles below the bot's highest role.

## Challenges

`challenges/types.ts`, `form.ts`, `cards.ts`, `actions.ts`: time-limited goals on the existing stats plus manually logged push-ups and custom goals (squats, steps, anything with a name), on their own dashboard page `/dashboard/challenges` (Overview nav → Challenges). The list page has All / Upcoming / Active / Completed filters with counts (`db.listChallenges` / `db.challengeStatusCounts`, effective status; internal status stays `ended`), Newest / Ending soon / Name sorting (`sort`, whitelisted ORDER BY), the challenges rendered as a table (`challengesTable`), and a 3-step server-only wizard (no JS) in `details#challenge-new`: details (name, description, goal type = `messages | reactions | voice | activity | pushups | custom`, activity name, optional goal name/label), schedule (optional target, start/end date, optional reward role), review. The destination comes from the dashboard Settings page, not the wizard: every new challenge is posted to `settings.challenge_channel_id` (default `#1575504788999639061`), one forum post per challenge in a forum/media channel (`challenges.thread_id` = the post) or one message per challenge in a text/announcement channel; existing challenges are not moved. `POST /challenge-wizard` validates every step with `parseWizardStep` and renders the next step with hidden inputs; `nav=back` renders the previous step from the same draft without validation, and steps 2–3 show a `Back` button. The final step inserts the row and its first goal, then posts the card (`createAndPostChallenge` deletes the row again if the send fails). A challenge has 1–5 goals; further goals are added on the overview tab (`POST /challenge-goal-add`, `parseGoal`). Dates are UTC days: empty start = now, the end date's whole day counts (`challengeWindow`); `defaultEndDate` = +7 days. A target is optional (`0`/empty = no target; `formatChallengeTarget` shows `no target`); when set it is a count for messages/reactions/push-ups/custom units and minutes for voice/activity. `goalName` shows the custom label or the metric/activity name. The detail page `/dashboard/challenges/:id` has Overview / Progress / Entries / Activity tabs (`?tab=`): overview starts with a compact `challengeMetaGrid` meta block, then goal standings plus the add-goal form, one ranked progress table per goal (no Share column for targetless goals), the manual-entry review table (`?flagged=1`, inline admin edit/delete), and the event log, with pagers.

- Tables: `challenges` (+ index `(guild_id, status, ends_at)`), `challenge_participants`, `challenge_events`, `challenge_goals` (+ index `(challenge_id, position)`) and `challenge_entries` (+ index `(goal_id, user_id)`), all `ON DELETE CASCADE`; `challenges.label` and `challenge_goals.label` hold the custom goal name (both migrated with `PRAGMA table_info` + `ALTER TABLE`), and `challenges.thread_id` holds the forum post for forum destinations (same migration). `createChallenge` inserts goal 1 in a transaction (copying the label); startup backfills one goal per legacy challenge (`WHERE NOT EXISTS`). Status is `upcoming | active | ended`; `createChallenge` stores `upcoming` when the start is in the future, and startup migrates old future-start `active` rows. `db.challengeTotals(guildId, metric, activityName, from, to, now)` returns progress per user: message/reaction counts in `[from, to)`, or the summed session overlap in ms for voice/activity (open sessions count up to `now`, clipped to the window); it returns `{}` for manual metrics. Manual progress is never stored as a total: `db.challengeEntryTotals(goalId, from, to)` sums `challenge_entries` per member, so edits update the row in place and deletes remove it (no double counting).
- Events: `challenge_events` (`kind` created/started/joined/left/ended/reward/goal_added/entry/entry_flagged/entry_edited/entry_deleted, optional actor and detail) feeds the Activity tab via `challengeEventText`/`CHALLENGE_EVENT_LABELS`. `createAndPostChallenge` logs `created`; `handleChallengeButton` logs `joined`/`left`; `beginChallenge` logs `started`; `handleChallengeLogSubmit` logs `entry` or `entry_flagged`; dashboard `POST /challenge-goal-add` logs `goal_added` and `POST /challenge-entry` logs `entry_edited`/`entry_deleted` with the admin id/name, old → new value and the optional reason (≤300 chars); `finalizeChallenge` logs `ended` (reward count) and one `reward` per granted member. Startup backfills `created`/`ended` events for challenges that predate the table.
- Card (`buildChallengeCard`): Components V2, one section per goal with every participant (`rankProgress`: value desc, ties by join time), value-only rows and a heading with `goalName` plus target or `no target`, join count, `Join`/`Leave`/`My progress` buttons and one `Log <goal>` button per manual goal (`challenge:my:<id>`, `challenge:log:<challengeId>:<goalId>`, at most 5 per row via `manualLogRow`; the same row is offered in the `My progress` and log-submit replies), no mentions; the tail is trimmed only when the 4000-char budget runs out, with a `-# +N more` line; text is trimmed to `TEXT_BUDGET`. Ended cards hide the buttons. `bot.ts` routes button interactions to `handleChallengeButton` (ephemeral reply/progress or modal) and modal submits to `handleChallengeLogSubmit`.
- Manual logging: only joined members inside `[startsAt, endsAt)` may submit; the modal takes an integer 1–5000 (`parseEntryValue`). Manual sets above 99 are still recorded but marked `flagged` (`shouldFlagEntry`) for admin review. A valid entry replies with the member's value / target / remaining per goal (no "still to go" line without a target), then refreshes the card immediately so every leaderboard is current.
- Progress is retroactive from the challenge start for everyone who joined (not from the join moment), and join/leave only changes who is ranked. Per-goal share is capped at 100% (`goalShare`); the overall challenge ranking (and reward order) is the mean share across goals with ties by join time (`overallRankProgress`).
- End: `finalizeChallenge` (idempotent `endChallenge`, accepts upcoming or active) grants the reward role permanently to the top 3 by mean goal share with progress > 0, then refreshes the card. `startChallengeTicker` (`scheduler.ts`, called from `index.ts`) walks `db.pendingChallenges()` every 60 s: `endsAt <= now` finalizes, `upcoming && startsAt <= now` starts (`beginChallenge`), otherwise refreshes active cards at most every 5 minutes. Admins can also end or delete a challenge from the dashboard (`/challenge-end`, `/challenge-delete` deletes the card message/post too).

## Free games

- Files: `freegames/types.ts`, `filters.ts` (`isBetaTitle`, `matchesFilters`, `filterGames`), `freestuff.ts` (FreeStuff webhook verify + normalizer), `cards.ts`, `form.ts` (dashboard form parsing), `actions.ts` (`announceInGuild`, `announceEverywhere`, `titleDedupeKey`).
- Source: the FreeStuff webhook only, no polling (Epic's free games arrive through it with store `epic`) (`POST /webhooks/freestuff` in `web/server.ts`, logic in `freestuff.ts`, enabled by `FREESTUFF_PUBLIC_KEY`; push-only, no REST key). FreeStuff cards show `-# via FreeStuff`. Console products from FreeStuff are skipped.
- **Dedupe**: every announce marks both `g.key` and `titleDedupeKey(g)` (`t:<platform>:<store>:<normalized title>`) in `free_posted`, and skips a game if either is posted. Use `announceInGuild` / `markGamesPosted` / `isGamePosted` from `actions.ts`, not raw `markFreePosted`. The webhook is signature-verified (Ed25519), replay-guarded, answers 204 first and announces asynchronously.
- Everything is normalized to `FreeGame` (`types.ts`): `key` is a stable id (`fs:<id>`), `kind` is `game | dlc | beta`, `platform` is `pc | mobile`, and `store` is one of `ALL_STORES`. Beta/playtest/demo keys are detected by `isBetaTitle`.
- Filters (`FreeSettings`: `stores`, `includeDlc`, `includeBeta` (default off), `includeMobile`) are applied by `matchesFilters` / `filterGames`. A new filter needs: the type, a DB column plus migration, `form.ts` parsing, the dashboard view, and the smoke tests.
- **No backlog**: webhooks only deliver new announcements, so nothing is seeded on enabling the feature or changing filters. Announce dedupe uses `markFreePosted` / `isFreePosted`. The dashboard status shows whether `FREESTUFF_PUBLIC_KEY` is set and the announced count.

## Dashboard / web

- `web/server.ts`: Hono routes, OAuth, settings POST handlers, data loaders (`loadOverview`, `loadEmojis`, `loadChallengesPage`, `loadChallengeDetail`, `loadLogs`, `loadRequests`), `GET /dashboard/live` (JSON `{ parts: { <element id>: <html> } }`, 401 JSON when logged out; `view` = overview | emojis | challenges | logs | requests | settings | session, the last takes `id`), `GET /dashboard/emojis` (emoji usage: all-time top 10, `?all=1` lists up to 500, `?emoji=<key>` picks the reactor leaderboard, unknown keys fall back to the first emoji), `GET /dashboard/challenges` / `/dashboard/challenges/:id` (missing or other-guild id = 404), `GET /dashboard/sessions/:id` (`loadSession`: transcript of one OpenCode session; the id must belong to a `build_jobs`/`chat_threads` row of the guild via `db.findSessionOwner`, else 404; fetch failure renders an error note), `/favicon.svg`, `/assets/clouds.png`.
- `web/views.ts`: server-rendered HTML and CSS. Seven pages share `layout()` (sidebar on desktop, top bar + bottom tab bar below 900px): Overview `/dashboard` (`dashboardPage`), Emojis `/dashboard/emojis` (`emojiPage`: `emojiList` links into the per-emoji reactor leaderboard), Challenges `/dashboard/challenges` (`challengesPage`) and one challenge (`challengeDetailPage` + `challengeTabs`), Settings `/dashboard/settings` (`settingsPage`), Requests `/dashboard/requests` (`requestsPage`), Logs `/dashboard/logs` (`logsPage`), Session `/dashboard/sessions/:id` (`sessionPage`/`sessionParts`, linked from the Requests tables, Requests nav item active, live regions `live-session-head`/`live-session` only on the newest page, no refresh with `?cursor=`).
- Pagination: every list that can grow is server-side paginated through the shared pure `pagerHtml` (views.ts; Previous / Page X of Y / Next, links get a `#h-...` anchor, no pager for one page): embeds 10 (`?embedsPage=`), Logs 50 (`?page=`, kept with `level`/`tag`; the level tabs and tag form reset to page 1; `db.recentLogs` offset + `db.countLogs`), Requests: feature requests 20 (`?page=`) and chats 20 (`?chatPage=`, total = threads + one-offs), each pager link keeps the other param; Challenges list 10 (`?status=`, `?page=`) and each detail tab 10 (`?tab=`, `?page=`), each pager link keeps the other param; the pagers live inside the `*Parts()` regions so `/dashboard/live` honours the params.
- Requests page rows (feature requests and chats) have no Session/Plan links: a row with a session has `data-href` plus a real `<a class="row-link">` (request title / "Started by" name), and `LIVE_SCRIPT` navigates on row click (delegated; skips links/buttons/forms, ctrl/cmd/shift/middle click opens a new tab). The session page head shows Cancel / Retry buttons (inline `confirm()`, POST forms) and a link to the job's other session.
- Cached tokens are shown as cache % (`cachePercent` = cacheRead / (input + cacheRead + cacheWrite)) everywhere in the dashboard.
- Live regions: `LIVE_SCRIPT` keeps `<details id>` elements open across swaps, so give every details element in a live region a stable id. Live regions are `<div class="live" id="live-...">`; each page renders them through its `*Parts()` function (`overviewParts`, `logsParts`, `requestsParts`, `chromeParts`), and the live endpoint returns the same functions' output, so add a region in the `*Parts()` function, never only in the page. `LIVE_SCRIPT` polls every 15s while the tab is visible; the Settings page never refreshes its forms (only the deployment chip).
- Background: `web/assets/clouds.png` (1-bit dithered cloud photo, white on transparent, CC0 source noted in `server.ts` and the README) drawn at natural size or an integer multiple (`--sky-size`), never `cover`; if the file changes, update `CLOUDS_VERSION` in `views.ts` (smoke checks the hash). `npm run build` copies `src/web/assets` to `dist/web/assets`.

## Chat assistant

`builder/chat.ts` + `chat-parse.ts`:

- Any member's @mention opens a thread backed by one OpenCode session (agent `chat`, `.opencode/agents/chat.md`, web search + read-only access to a checkout of `main` at `/workspace/bojan`, refreshed with `OpenCodeAgent.refreshMain` before each new chat session).
- The bot only answers messages that @mention it or reply to one of its messages (`isDirectedAtBot`); every other thread message produces no model call, reaction or typing and is not buffered: on each directed turn `ChatRunner.fetchContext` fetches the thread's messages from Discord (up to 50 before the batch, only those after the bot's last message, `sinceLastBotMessage`; fetch failure = no context) and prepends them under "Other messages in the thread since your last reply" (`formatThreadContext`), so context survives restarts.
- Directed messages are batched (3s debounce, serialized per thread) and always answered when the agent produced visible text (the json `reply` flag is ignored).
- Decision model: `chatDecisionModel` (default `opencode-go/jev-1.14`, `OpenCodeAgent.decide` → `experimental.generate.decisions`, predicate `FEATURE_REQUEST_QUESTION`, `isFeatureRequest` threshold 0.5, 15s timeout; failure = plain chat) runs only for a directed (@mention) message from an admin while building is enabled and configured (`shouldRunDecision`; also for one-off mentions, before any session is created), and sees the last ~30 thread messages before it (history, clipped to 6000 chars), the replied-to message and the "Latest message (the one to classify)" (`formatDecisionInput`), so a short "ship this" / "build it" referring to a bot change discussed earlier counts as a feature request while discussing alone does not.
- If it says yes the chat agent is skipped: the build job starts in the same thread (`BuilderRunner.startJob` with the plain request text from `featureRequestText` and a transcript of up to 50 recent messages; the planner prompt says the request may refer to the discussion in the transcript, which never approves a plan) and "Got it, I'll make a plan for this." is posted only after `startJob` succeeded; pending notes stay for the next chat turn; after the job ends the thread is chat again.
- Everyone else (non-admins) who mentions the bot goes to the chat agent, which, for a change request, asks them to say clearly what to build (e.g. "@bojan build <the change>") or to say "ship this" after discussing it in the thread.
- The agent ends with a trailing json block `{reply}`; a reply without a valid block is never posted (asked once more, then dropped, `ChatReply.missingBlock`).
- Build status changes queue `[build update]` notes (`formatBuildNote`, `chat_threads.pending_notes`) that are prepended to the thread's next chat prompt (no model call of their own).
- Mentions inside foreign threads are one-off replies.
- State: `chat_threads` table, `chatEnabled`/`chatModel`/`chatDecisionModel` in `getBuilderSettings`. `chat-parse.ts` is pure (reply parsing, chunking to 2000 chars, prompt formatting).
- The `[build status]` block (`formatJobStatus`, `jobStatusBlock`) for the thread's newest in-flight job is prepended to chat turns, so chat keeps working during a job; while a job is active the decision model is skipped (no second job). `chat-parse.ts` also has `pickReplyTarget`.
- Images: attachments (max 4, 5 MB each, `selectImages` + `images.ts` `downloadImages`) of the directed message and its replied-to message are downloaded and sent as inline `data:` URIs in `session.prompt` `files` (chat turns, one-off replies, the feature request's first planner turn and directed planner replies; thread context and build prompts stay text).
- Feedback is via reactions (`builder/reactions.ts`): directed messages (mention or reply to the bot) get the guild's `hmmmm` emoji (fallback 🤔) until the turn ends, typing is shown only for turns with a directed message, and the first reply chunk is a Discord reply to the target message. The runner has no typing indicator: 📝 on the triggering message while planning, 🔨 on the plan message while building, then ✅ (PR opened) or ❌ (failed); `updatePresence` sets the bot activity to `Building <title>` (`buildingActivity` in `queue.ts`).

## Self-building (`builder/`)

- `queue.ts` (pure: queue order/slots, recovery decision, conflict action, resume/fix prompts), `parse.ts` (agent reply/json parsing, `prInfoFromJson`, naming, usage formatting, admin check; pure), `cards.ts` (Components V2 cards, pure), `opencode.ts` (`@opencode/client` wrapper: warm location, git worktree via shell, session, prompt-and-wait (`session.wait` is bounded to 60s slices, no warning for our own aborts, optional `onProgress` per slice), usage, Go limit meters).
- `limits.ts` (OpenCode Go quota gate: refuses chat/plan/build model calls while any 5h/weekly/monthly meter is at `limitThreshold` % — dashboard setting, default 95 — and answers with the reset time; 30s cache, fail-open).
- `runner.ts` (orchestration): plan Q&A in parallel per thread; the build runs in a FRESH `feature-build` session that gets only the request and the approved plan (`buildPrompt`, plan text = `build_jobs.last_plan`, kept current at approval); the planner session id moves to `build_jobs.plan_session_id` and `session_id` becomes the build session; old jobs with `plan_session_id` null keep building in the shared session; job usage is the sum of both sessions (`addUsage`). Build queue limited by `maxParallelBuilds` (statuses `queued`/`building`, FIFO by `approved_at`, drained when a build ends, on a 30s tick and after recovery). Token usage is refreshed in the DB while a session runs (`onProgress` = `saveUsage`). Restart recovery resumes interrupted sessions (max 2, `resume_count`). PR tracking via GitHub API every 2 min with one automatic merge-conflict fix per PR (`fix_attempts`).
- `handler.ts` (messageCreate): thread messages feed the runner while a job is active, otherwise the chat assistant. In the planner phase only directed messages (mention or reply to the bot, e.g. to the plan card) trigger a turn via `handleReply(..., { trigger })`, other messages are context only (`preContext`, header "Other thread messages since your last reply") and can never approve. A directed message sent while a planner turn runs triggers one revising turn right after it (`followUps`, `followUpPrompt`; the stale reply of the running turn is held back and not posted unless it is an error or cancellation (`shouldHoldPlanReply`), and follow-up turns never approve (`noApprove`)). No bot output for non-directed messages in any path.
- Dashboard cancel/retry: `BuilderRunner.cancelJob` (allowed per `canCancel`: planning/awaiting_input/queued/building) sets `cancelled` FIRST, clears the planner buffers, then calls `OpenCodeAgent.interrupt` on the current session (errors only warned), posts `buildCancelledCard`, notes the chat and drains the queue. `fail`, `failFix`, `handlePlanReply`, `handleBuildReply`, `handleFixReply`, `runTurn` and `retryTransient` re-read the status and do nothing for a cancelled job, so the interrupted run's late "aborted" result never overwrites it. `retryJob` (failed jobs only, `retryAction`): `build` (approved + non-empty plan) clears the error, queues the job and drains; `runBuild` then sends `BUILD_ERROR_RETRY_PROMPT` into an existing build session that already answered (else the full build prompt); `plan` (session but no approval) goes back to `awaiting_input` and runs a planner turn with `PLAN_ERROR_RETRY_PROMPT` flagged as follow-up so it can't approve. Routes: `POST /dashboard/requests/:id/cancel|retry` (`?back=session` returns to the session page).
- Jobs live in `build_jobs` (a thread may hold several over time; `getBuildJobByThread` returns the newest); settings via `getBuilderSettings` (bot_state). Needs `OPENCODE_PASSWORD`; agents are defined in `.opencode/agents/`.

## Transcript page

`builder/transcript.ts`: pure view model of an OpenCode session for the dashboard session page (`normalizeTranscript` clips text/tool input/output, tolerates unknown message types; assistant entries carry `timing` (first token, total, tools, retry) and every entry `gapMs` (idle since the previous entry ended), shown under each message; `fetchTranscript` pages `client.message.list` newest-first, 8s timeout).

The session transcript is newest first (`fetchTranscript` returns newest first, 30 messages per page, parts inside one message stay chronological) with "Latest messages" / "Older messages" links below it.

## Discord requirements

- Gateway intents (`bot.ts`): regular intents Guilds, GuildMessages, GuildMessageReactions, GuildVoiceStates; privileged intents MessageContent, GuildMembers, GuildPresences. The privileged ones must be enabled in the developer portal.
- Bot permissions: View Channels, Send Messages, Read Message History, Embed Links, Attach Files (weekly chart PNG), Manage Messages (embed converter deletes or suppresses the original), Manage Webhooks (embed converter reposts), Create Public Threads + Send Messages in Threads (self-building request threads), Add Reactions (status emoji; Use External Emojis is not needed), Manage Roles (name-colour roles; the roles must be below the bot's highest role). OAuth scopes `bot` + `applications.commands`. The dashboard allows Administrators or `ADMIN_ROLE_ID`. Setup details are in `README.md`; env vars are in `.env.example`.

## Overview

The bot tracks message/reaction/voice/activity stats, posts weekly stats, converts embed links, announces free games, and serves a Hono dashboard with Discord OAuth. Charts are rendered to PNG with `@resvg/resvg-js`. User-facing docs and setup live in `README.md`; `CLAUDE.md` covers working in the code.
